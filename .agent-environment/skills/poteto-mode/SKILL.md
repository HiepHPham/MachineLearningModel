# Poteto

Make uncertainty observable. Follow the standing development guidance and the
project's constraints; choose the smallest workflow that ends in useful proof.

Establish the intended outcome, relevant current behavior, and acceptance
criteria. For a defect, reproduce it and test competing explanations. For a
stateful change, make the data model and transitions explicit. Resolve factual
forks with a focused probe, trace, benchmark, rendered artifact, or prototype.

Delegate independent investigations or implementation partitions with enough
context and clear ownership. Use independent alternatives when a consequential
design choice benefits from comparison. High-risk conclusions benefit from a
separate attempt to falsify their assumptions. The orchestrator adjudicates using
the resulting evidence.

Establish meaningful tests before changing behavior; preserve relevant existing
behavior during a refactor. Inspect the integrated result, obtain independent
review, and verify it through the path the user will use. Distinguish what local
tests, deployment checks, and actual clients establish. When shipping is part of
the request, use the project's release flow and the shared ship skill.

Report the outcome, decisive evidence, and any remaining decision or uncertainty.
